“It’s Only a Small Change.” — One of the Most Dangerous Sentences in Project Management

Small development effort does not always mean small project impact. The real question is whether the request changes something already approved or baselined.

By OV Prakash · September 2026

During an ERP implementation, we often hear: “It’s just one additional field.” “It’s only a small workflow change.” “Development will take just eight hours.” Or even, “Do we really need a Change Request?”

When does a small requirement become a Change Request?

From a PMI-aligned project management perspective, size alone is not the deciding factor. The first question should be whether the request changes something that has already been approved, baselined or otherwise placed under project control.

Key question: Does this request change something that has already been approved or baselined?

If the requirement is already within the approved scope, it may simply be clarification or execution of an existing requirement. If it proposes a change to approved scope or another controlled project element, it should be evaluated through the project’s agreed change-control process.

A practical change-control flow

New Request → Check Against Approved Scope / Requirements → Assess Impact → Raise Change Request (if required) → Review & Approval → Update Affected Plans / Baselines → Implement & Validate

Why a “small” ERP change can have a bigger impact

An eight-hour development change may still require much more than eight hours of project effort. The broader impact can include:

  • Solution and design review
  • Security assessment
  • Additional or regression testing
  • User Acceptance Testing (UAT)
  • Documentation updates
  • Training and change communication
  • Deployment activities
  • Additional support and hypercare
8 hours of development ≠ 8 hours of project impact.

Change control is not bureaucracy

Good change management is not about making every request difficult. It is about ensuring stakeholders understand the full impact before making a decision.

Not every new request necessarily needs a formal Change Request. The agreed change-management approach should define how proposed changes are evaluated, who has authority to approve them, and how affected project information is updated.

What matters is that the project team does not judge a request only by coding effort. Scope, schedule, cost, quality, risk, testing, deployment, business readiness and downstream dependencies may all need consideration.

The takeaway

Small effort does not always mean small impact. Strong project governance creates visibility before commitment, so the project can make an informed decision rather than discover the consequences later.

A useful leadership question: How does your project decide when a requirement should become a formal Change Request?
